# Cleanup Wave 1 — the test safety net

**Status:** awaiting Rishi review. No test files touched yet.
**Parent:** `docs/cleanup-plan-2026-07-27.md` (Wave 1 = PR4/PR5/PR6 there).
**One-line:** before we refactor anything structural (Waves 2–5), build tests that
tell the truth when code changes — because today's 1,365 tests do not.

---

## Part 0 — What this wave is, and is not

- It adds **zero runtime code.** Every change is CI, test files, and one pytest
  config block. The running service is byte-identical after all three PRs.
- It is the wave that makes the **risky Wave 2** (background-worker split) and
  Wave 4 (auth) survivable — because after this wave, a refactor that breaks chat
  turns CI red *before* merge, and a deploy that breaks chat turns the smoke test
  red *after* merge (auto-rollback fires).
- It changes **how we know things work** from "the source still contains this
  string" to "the product still does this thing against a real Postgres."

---

## Part 1 — Baseline (the why, in numbers)

From the 2026-07-29 audit of `tests/`:

| Fact | Number |
|------|--------|
| Test files | 130 (`129 test_*.py` + `__init__.py`) |
| Tests collected | **1,365** (in 0.18s — nothing does I/O) |
| Files that `.read_text()` source and assert on substrings | **98 of 129** (364 call-sites) |
| **Pure** source-inspection files (never import an app module) | **49 (~38%)** |
| Files that exercise real app behavior | ~38 |
| Tests that touch a real database | **0** |
| Files with a hand-rolled `sys.path` block | **71** |
| `conftest.py` / `pyproject.toml` / `pytest.ini` | **none exist** |

**The core gap.** Every "DB test" runs against a hand-rolled fake pool that returns
canned rows — often branching on SQL *substrings* (`if "collage_date" in sql`). A
stub that matches on SQL text can never see a real type codec, a real constraint,
or a real transaction.

**The smoking gun — `app/routes/chat.py:531-544`** (`_parse_collage_date`):

> asyncpg's DATE codec requires a `datetime.date` object — passing a string raises
> `DataError` and the whole `POST /messages` 500s… Discovered 2026-07-14 from
> Sarvesh integration: **PR #456's tests passed a real `date` object through the
> mocked pool and never exercised the real asyncpg codec.**

The test asserted the mock behaved like the mock. Production sent an ISO string and
500'd at the codec layer before any SQL ran. **~15 tests against a real Postgres are
worth more than the 1,365 we have** — and they are what let us refactor aggressively
later.

**Two more real-DB-only hazards the audit surfaced** (future regression targets):
- `_can_access_conversation` (`chat.py:275`) has **4 allow-branches + default-deny**,
  shared across **5 call-sites** — the exact "change the shared helper, not one
  endpoint" shape that bit us before. Stub pools can't verify all four paths.
- TOCTOU check-then-INSERT windows flagged in comments at `chat.py:621` and `:967`
  — invisible to stub tests, visible to a real-DB concurrency test.

## Part 2 — Corrections to the plan-as-written

Building the real harness turned up three things the parent plan got slightly wrong.
None change the shape of the wave; all change the details:

1. **Test DB image = `pgvector/pgvector:pg15`, not `postgres:16`.** Migration 008
   enables the `pgvector` extension; plain Postgres fails to apply the schema. And
   `migrations-ci.yml` **already** stands up exactly this image as a GitHub Actions
   service and applies every migration via `psql` — so PR6 reuses a proven pattern.
2. **The smoke workflow already exists** (`post-deploy-smoke.yml`) and is wired to
   auto-rollback. It runs *public endpoints only* and explicitly defers the
   authenticated chat path "to the PR." So PR4 is an **extension**, not a new file.
3. **The count is 1,365, not 1,364.** The invariant for PR5 is 1,365 → 1,365.

## Part 3 — The harness decision — ✅ DECIDED: Option B (2026-07-29)

**Rishi chose Option B — testcontainers.** The integration tests spin their own
`pgvector/pgvector:pg15` container so they run identically on the Mac and in CI. The
options are kept below for the record.

**How do the integration tests get their real Postgres?** This is the only genuine
fork; everything else I've defaulted with a recommendation.

**Option A — GitHub Actions service.** Copy `migrations-ci.yml`'s `pgvector/pgvector:pg15`
service block into the `test` job; a step applies the migrations; integration tests
connect over TCP.
- ➕ Zero new dependencies. Reuses a pattern already in the repo.
- ➖ The real-DB tests run **only in CI**. Locally, `pytest tests/` still can't run
  them unless you hand-start a Postgres. Two classes of test (unit vs integration),
  two ways to run them.

**Option B — testcontainers (recommended).** Each test session spins its own
`pgvector/pgvector:pg15` container (the pattern in the conftest reference we
preserved at `docs/testing/wave1-conftest-reference.py`).
- ➕ **Identical locally and in CI.** You can run the real DB tests on your Mac with
  one `pytest` command — which is what makes a safety net actually get used before a
  push. Self-contained; no CI service wiring.
- ➖ One new dev dependency (`testcontainers[postgres]`) and ~3–5s container startup
  per session. Needs Docker available (GitHub runners and your Mac both have it).

**My recommendation: B.** A refactor safety net only helps if you run it while
refactoring, and that means locally. The cost is one dependency and a few seconds.

*(Everything below assumes B; if you pick A, only PR6's harness step changes — the
test list and isolation strategy are identical.)*

## Part 4 — PR-by-PR

Execution order: **PR5 → PR6 → PR4.** PR5 is the foundation the new tests are written
on; PR6 is the core net; PR4 needs one manual step from you (a real test JWT), so it
lands last / in parallel. One PR in flight at a time (Rule 6).

### PR5 — pytest config + `conftest.py` (foundation)
**Goal.** Add a `pyproject.toml` with `[tool.pytest.ini_options]` (`pythonpath`,
`testpaths = ["tests"]`, `asyncio_mode`) and a root `conftest.py`. Delete the 71
hand-rolled `sys.path` blocks. Imports stay exactly as they are (`from routes.chat
import …`) because `pythonpath` puts `app/` on the path — so this is a *deletion*, not
a rewrite.
**Blast radius.** CI only. No runtime code.
**Reversibility.** Trivial (revert one commit).
**Size note.** Touches 71 files, but every change is removing identical boilerplate.
Large-but-mechanical, single-concern. Not the ">100 new lines, stop and ask" case
(Rule 8) — it's ~200 lines *deleted*.
**Concept — one import root.** There's no `conftest.py` today, so each of 71 files
patches `sys.path` itself. That's 71 copies of one workaround, each free to drift.
One config line replaces all of them.
**Verify.** `pytest tests/` collects **1,365 → 1,365**, identical pass count, locally
and in CI. Any delta means we broke collection — that's the whole test.

### PR6 — real pgvector Postgres + first integration tests (the core)
**Goal.** Stand up a real `pgvector/pgvector:pg15` for the test session (Option B: via
testcontainers in `conftest.py`), apply `migrations/*.sql` in order against it, and
write **~15 integration tests** that use a real asyncpg connection. See Part 5 for the
migration adaptation and Part 6 for the exact test list.
**Blast radius.** CI only. Adds ~2 min to CI and makes it far more truthful.
**Reversibility.** Revert the workflow/conftest change; delete the new test file.
**Concept — doubles vs. integration.** 1,365 tests, zero touch a DB. The codec bug
(Part 1) is the proof: a stub that matches SQL substrings can't catch a driver-layer
type error. Fifteen real-DB tests buy more safety than the 1,365 we have.
**Verify (the acceptance test for this whole wave).** On a throwaway branch,
*reintroduce* the `collage_date` string bug (pass a str where asyncpg wants a `date`).
The new suite must go **red**. If it doesn't, the harness isn't wired to the real
codec and PR6 isn't done. Also re-verify all four `_can_access_conversation` branches
with a real row.

### PR4 — authenticated smoke test (needs one thing from you)
**Goal.** Extend `post-deploy-smoke.yml` past public endpoints to the real product
path: create conversation → send message → assert an assistant reply → SSE stream
yields tokens → delete conversation. Against a dedicated throwaway test user + test
bot on the live service, post-deploy, wired to the existing auto-rollback.
**What I need from you.** A **real, signed JWT** for a throwaway principal, stored as a
GitHub secret. It **must** come from the real issuer, not a hand-minted unsigned one
— otherwise Wave 4's signature-verification (PR14) will break this smoke test at
exactly the moment we most need it. This is the only manual step in the wave.
**Blast radius.** None to the service; it only reads prod after deploy, plus creates
and deletes one conversation per deploy.
**Reversibility.** Delete the job.
**Concept — "up" vs "works".** `/health` 200 means the process booted. It says
nothing about whether chat works — and that gap is where every interesting outage
lives. The smoke test is the automated version of you opening the app after a deploy,
and it acts (rollback) even when you're asleep.
**Verify.** Break a route on a branch; confirm the smoke job goes red and dispatches
rollback.

## Part 5 — Migration-into-testcontainer adaptation

The preserved reference shells out to `alembic upgrade head`. v2 has no Alembic. The
harness must instead replay the numbered SQL the way `run-migrations.sh` does, minus
its production coupling:

- **Discover + order:** `sorted(glob("migrations/*.sql"))` excluding `*.down.sql` —
  47 files, lexical order = numeric order.
- **Apply each file** in its own transaction against the container's asyncpg
  connection (mirrors the runner's `BEGIN … COMMIT` per file). Record applied names
  in a `schema_migrations` ledger so behavior matches prod.
- **Strip the prod-only coupling:** no Patroni `docker exec` (connect over TCP to the
  container), skip the empty-ledger refusal (`FORCE_RUN_ON_EMPTY_SCHEMA_MIGRATIONS`
  path), and skip the `pg_dump`-to-S3 pre-migration step (`PRE_MIGRATION_DUMP_ENABLED=false`).
- **Session-scoped:** migrate once per pytest session; isolate per test by
  **TRUNCATE-and-reseed** of the tables each test touches (recommended over
  transaction-rollback, because chat-send commits its own writes internally, which a
  wrapping rollback wouldn't cleanly isolate). Same shape as the reference conftest.

A bonus test worth including: a **schema round-trip** test that simply applies all 47
migrations against a fresh container and asserts success — that alone would have
caught several classes of migration bug before deploy.

## Part 6 — The ~15 first-coverage tests

Chosen to cover the highest-risk, most-refactored surfaces (all against the real DB):

1–3. **Chat send** — happy path inserts a user message + returns an assistant reply;
     bad-auth 401/403; the **`collage_date` codec regression** (str input must not 500).
4.   **Chat SSE stream** — streaming a reply yields tokens and terminates cleanly.
5–8. **`_can_access_conversation` — all four allow-branches** (owner, influencer,
     parent-principal, participant_b) each with a real row + default-deny.
9.   **H2H recipient access** (participant_b path) end-to-end through one endpoint.
10.  **Collage message persistence** — the real insert + read-back (the stubbed area
     from the codec bug).
11.  **ETL drain** — one drain cycle against real tables.
12.  **Conversation create + delete** — lifecycle used by the smoke test, verified
     against the DB.
13.  **Rate-limit config read** — real row, real types.
14.  **Migration round-trip** — all 47 apply cleanly to a fresh container.
15.  **Pool/health** — `get_pool()` + `check_db_health()` against the real container.

This list is a starting contract, not a ceiling; it's deliberately ~15 so the wave
stays reviewable.

## Part 7 — What we do NOT touch, and abort criteria

**Do not touch in Wave 1:**
- Any runtime code in `app/`. If a test can't be written without changing app code,
  that's a Wave 2+ finding — note it, don't fix it here.
- The 49 pure source-inspection tests. They're low-value but harmless; deleting them
  is Wave 5 (docs/test hygiene), not now. Mixing deletion into this wave muddies the
  "count invariant" proof.
- The migration files themselves, the runner's prod path, Patroni, WAL-G.

**Abort criteria (stop, reassess):**
- PR5 changes the collected test count off 1,365 → collection broke; fix before merge.
- CI time grows beyond ~+3 min → revisit Option A vs B / container reuse.
- The PR6 acceptance test (reintroduced codec bug) does **not** go red → the harness
  isn't real; do not merge PR6 until it does.
- Any flakiness in the new DB tests across 3 CI runs → fix isolation before adding more.

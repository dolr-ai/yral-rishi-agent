## 1. Why this is the right move (and what's actually missing)

The morning's Layer 1 integrity check (2026-05-30 08:20 UTC, watermark 2026-05-29 23:35) revealed:

| Table | chat-ai | V2 | Diff |
|---|---|---|---|
| messages | 3,343,812 | 3,335,246 | **-8,566** |
| conversations | 285,514 | 284,843 | **-671** |

**Important re-read of the data:** V2 has 99.74% match — it's not missing the entire pre-2026-05-26 horizon. The Day-9 one-time ETL (Phase 1.14, 2026-05-25) imported ~all chat-ai history. So the 8,566/671 gap is **NOT** a horizon-cutoff issue.

The probable gap source is the **~4-day operational window between Day-9 ETL (2026-05-25) and incremental cron start (2026-05-29 16:14)**. During that window:
- Chat-ai received new conversations + messages
- V2 had no ETL running
- When incremental started, its cursor was `2026-05-26T00:00:00` — so rows with `created_at > 2026-05-26` were caught, but Day-9's snapshot was already from BEFORE that

If Day-9 ran at `2026-05-25T18:00` (estimate), and incremental's cursor is `2026-05-26T00:00:00`, there's a **6-hour gap** where chat-ai activity went unrecorded. Plus any rows the Day-9 ETL missed for other reasons.

**Why re-bootstrap regardless of "only 0.26% is missing":** A4 doesn't say "99.74% is good enough." It says all data must port. The re-bootstrap is the belt-and-suspenders move — re-ingest from epoch with `ON CONFLICT DO NOTHING`, and any row already in V2 is a fast no-op. The cost is throughput; the benefit is provable completeness.

## 2. Cursor handoff strategy

**The boundary is static, not negotiated.** Two independent pipelines, strict timestamp boundary:

| Pipeline | Filter | Source |
|---|---|---|
| **Re-bootstrap** (this design) | `created_at < '2026-05-26T00:00:00+00:00'` | chat-ai S3 backup → sidecar pg → CSV |
| **Incremental** (already running) | `created_at >= '2026-05-26T00:00:00+00:00'` | rishi-1 cron → CSV → S3 |

The two paths never overlap. The incremental cursor (`~/.etl-export/state.json` on rishi-1) is NOT TOUCHED during the bootstrap. Incremental keeps emitting tick/hourly/sample/sentinel payloads on its 5-minute cadence; V2 keeps applying them. The bootstrap is additive — more CSVs into the same S3 prefix, V2's existing apply logic consumes them.

**Edge case at exactly midnight 2026-05-26:** mathematically possible but practically nil. Safety net: `ON CONFLICT DO NOTHING` means any duplicate at the boundary is silently absorbed. No special handling needed.

**Why this beats "rewind the incremental cursor backward":**
- Rewinding would race with the incremental's forward apply (two writers, same files)
- Rewinding requires pausing incremental, which means a freshness window where new chat-ai activity isn't being captured
- The static boundary preserves the incremental's existing health (V2 is matched to within minutes of real-time on the forward side)

## 3. Dump source — Option B (S3 backup) recommended

### Option A — Fresh pg_dump from rishi-2 (chat-ai Patroni leader)
- **Pros:** Fresh data; we control filter/format directly
- **Cons:** Load on chat-ai production leader during the 15-30 min dump; egress from chat-ai → V2 cluster; one more pg_dump touches chat-ai's running prod DB
- **Verdict:** Workable but adds production-side risk we don't need

### Option B — Reuse chat-ai's existing S3 backup pipeline ✅ **RECOMMENDED**

I confirmed via read-only S3 listing today (no production touches):

```
yral-chat-ai/daily/2026-05-28_053300.sql.gz   520 MB
yral-chat-ai/daily/2026-05-28_092653.sql.gz   520 MB
yral-chat-ai/daily/2026-05-28_132840.sql.gz   521 MB
yral-chat-ai/daily/2026-05-28_172430.sql.gz   521 MB
yral-chat-ai/daily/2026-05-28_205352.sql.gz   521 MB
yral-chat-ai/daily/2026-05-29_010954.sql.gz   521 MB
... (every ~4 hours, 14-day retention)
```

Each backup is the full chat-ai database, ~520 MB compressed (likely 3-5 GB uncompressed). Generated by chat-ai's own backup pipeline (see `chat-ai-db-stack/project.config`), already battle-tested for DR purposes.

- **Pros:**
  - **Zero chat-ai production load** — backup already exists, we just download it
  - We've already proven we can read this bucket (the ETL incremental uses the same credentials)
  - Backup format is `pg_dump --format=custom` (we use the same on V2 nightly)
  - 14-day retention is plenty of headroom
- **Cons:**
  - Backup is from up to ~4h before bootstrap start — but the 2026-05-26 boundary is months earlier, so freshness is moot
  - Requires a sidecar pg instance to restore into (not free — but cheap)

### Decision: **Option B, with the most recent `daily/*.sql.gz` available at execution time**

## 4. Staging area

### 4a. Sidecar Postgres instance (not V2's production cluster)

Restore the chat-ai backup into a fresh, isolated Postgres instance — not the running Patroni cluster on rishi-4/5/6.

**Provisioning:** `docker run -d --name chat-ai-restore-sidecar -v /var/lib/restore:/var/lib/postgresql/data postgres:16` on rishi-5 (where there's known free disk per earlier ops). 50-80 GB volume to hold the restored DB (3-5 GB data + WAL headroom). Tear down after extraction.

**Why a separate sidecar, not V2 prod:**
- V2 is serving live traffic; we don't want a 3-5 GB restore touching its shared buffers
- Schema differences: chat-ai may have indexes/triggers V2 doesn't (or vice-versa). Restore-into-prod risks accidental schema collisions
- Isolation makes rollback trivial: drop the sidecar container, disk goes away

### 4b. Extraction (sidecar → S3 CSVs)

Once the sidecar has the chat-ai snapshot, run the existing `scripts/incremental_export.py` pattern against it — but with a hardcoded `--where created_at < '2026-05-26T00:00:00+00:00'` filter and a different filename prefix (`historical_<table>_<chunk>.csv.gz`).

**Chunking:** 50,000 rows per CSV file (matches incremental's `PAGE_SIZE`). For 3.3M messages, that's ~66 files. Each ~5-10 MB compressed.

**Upload destination:** `s3://rishi-yral/yral-chat-ai/incremental-sync/` — **same prefix as incremental**, so V2's existing apply logic consumes them naturally. The `historical_` filename prefix is purely for human/audit identification; V2's `_FILENAME_RE` regex needs a small extension to recognize it (see section 7 — code changes).

### 4c. Apply order (FK dependency)

`ai_influencers` → `conversations` → `messages`. Out-of-order apply produces orphan messages.

**Mechanism:** sequential upload waves with explicit drain barriers:
1. **Wave 1:** all `historical_ai_influencers_*.csv.gz`. Wait for V2's `etl_processed_files` to show all wave-1 filenames processed.
2. **Wave 2:** all `historical_conversations_*.csv.gz`. Wait for drain.
3. **Wave 3:** all `historical_messages_*.csv.gz`. Wait for drain.

Per-wave verification (Layer 1) at each barrier — section 6.

## 5. Load impact estimate

### 5a. Row counts (epoch → 2026-05-26)

V2 currently has `~3.3M messages` and `~285K conversations`. Per the 99.74% match read in section 1, chat-ai's total is essentially the same. So the bootstrap re-processes the same volume V2 already has — **but `ON CONFLICT DO NOTHING` makes ~99.74% of rows a no-op INSERT.**

| Table | Estimated rows | Net new (best estimate) |
|---|---|---|
| ai_influencers | ~5,000-10,000 | 0-10 (V2 has the full set via Day-9) |
| conversations | ~285,000 | 671 (matches Layer 1 diff) |
| messages | ~3,343,000 | 8,566 (matches Layer 1 diff) |

### 5b. Pipeline duration estimate

| Stage | Estimated time |
|---|---|
| Sidecar provision + pg restore | 30-45 min (3-5 GB pg_restore is I/O-bound) |
| CSV extraction (`\COPY` per chunk) | 60-90 min |
| Upload to S3 (66 message files × ~10 MB each, plus conv + influencer) | 10-15 min |
| V2 apply (already-known per-file rate: 5-10 files per 5-min tick) | **3-5 hours** |
| Verification (Layer 1 + sample) | 30 min |
| Sidecar teardown | 5 min |
| **Total wall-clock** | **5-7 hours** |

### 5c. V2 production impact during apply

- ETL apply uses `CREATE TEMP TABLE ... LIKE` + COPY + INSERT — staging tables are session-local, no cross-replica contention
- Each apply tick is ~150-300 ms (current measurement) — negligible relative to V2's request budget
- `ON CONFLICT DO NOTHING` short-circuits on existing rows, so the dominant cost is CSV download + COPY parse, not DB-write
- **No expected user-facing latency impact.** Incremental ETL has been running alongside live traffic for two days with no measurable degradation per beszel-agent.

### 5d. chat-ai production impact

**Zero.** The backup is already on S3 from chat-ai's existing pipeline. We pull from S3, not from rishi-2. The sidecar restore touches no chat-ai resource.

## 6. Verification plan

### 6a. Per-wave drain check (during apply)

After each wave (influencers, conversations, messages) finishes uploading, poll `/admin/etl-status` until `files_processed_24h` shows all wave files in `etl_processed_files`. Block before starting the next wave.

### 6b. Layer 1 (row count) — after all waves apply

Query V2: `SELECT COUNT(*) FROM messages WHERE created_at < '2026-05-26T00:00:00+00:00'`. Same for conversations + ai_influencers.

Query sidecar Postgres (still running at this point): same count, same filter.

**Acceptance:** V2 count == sidecar count within tolerance of `etl_skipped_rows` for the `historical_` filenames. Tolerance == count of Option-A-skipped rows from the bootstrap (`SELECT COUNT(*) FROM etl_skipped_rows WHERE filename LIKE 'historical_%'`).

### 6c. Layer 2 (sample + content hash) — historical slice

Pick 50 random conversations with `created_at < '2026-05-26'`. For each:
1. Fetch full row from sidecar Postgres + V2; compare via the canonicalize-for-compare helper (already shipped in PR #226 — handles the microsecond-precision issue).
2. For each message in the conversation: fetch from both sides; compare `content_sha256` (Python-side, matches the existing Layer 2 sample protocol).

**Acceptance:** 0 unexplained mismatches (`mismatches.len() == 0` OR all mismatches are in `etl_skipped_rows` with reason `conflict` or `orphan`).

### 6d. Layer 3 (sentinel) — boundary message

The LATEST pre-2026-05-26 message (by `created_at`) on the sidecar should exist in V2's `messages` table with matching `content_sha256`. This is the highest-risk row — it's the one closest to the boundary and most likely to be missed by an off-by-one bug.

### 6e. Integrity verifier re-run

After the bootstrap completes, re-trigger the Layer 1 hourly check for a watermark BEFORE 2026-05-26 (e.g., `2026-05-20T00:00:00`). The diff should be **0 ± Option-A-skip count**.

## 7. Code changes required

Bootstrap reuses ~95% of the existing pipeline. The small additions:

### 7a. `scripts/historical_export.py` (new — modeled on `incremental_export.py`)

- Reads from sidecar pg (not chat-ai's Patroni)
- Hardcoded `WHERE created_at < '2026-05-26T00:00:00'` filter
- Iterates over `ai_influencers`, `conversations`, `messages` in dependency order
- Outputs `historical_<table>_<chunk_id>.csv.gz` files to the same S3 prefix
- Emits `_integrity/historical_<wave>_complete.marker` between waves
- Single-shot: runs to completion, does not loop

### 7b. `app/services/etl_chat_ai.py` regex extension

Currently:
```python
_FILENAME_RE = re.compile(r"^(?P<ts>\d{8}T\d{6}Z)_(?P<table>[a-z_]+)\.csv\.gz$")
```

Extended:
```python
_FILENAME_RE = re.compile(
    r"^(?:historical_(?P<chunk>\d+)_(?P<table_h>[a-z_]+)"
    r"|(?P<ts>\d{8}T\d{6}Z)_(?P<table>[a-z_]+))\.csv\.gz$"
)
```

The apply logic doesn't change — staging+COPY+INSERT ON CONFLICT DO NOTHING handles both shapes.

### 7c. (Optional) Single-flight lease on apply

The V2-replica race we deferred earlier (one file processed by both replicas, second gets PK-conflict no-op) is harmless during normal operation but wastes ~2× the apply work during a 5-hour bootstrap. **If we want to make the bootstrap finish faster**, this is the time to add a `SELECT FOR UPDATE` lease on `etl_processed_files` so only one replica picks up each file.

**Recommendation:** ship without the lease change first. If apply runtime > 6 hours becomes a problem, add the lease as a follow-up PR.

### 7d. New `migrations/024_historical_bootstrap_marker.sql` (optional)

A single-row marker table to record bootstrap start/end/status. Useful for ops visibility and to prevent accidental concurrent bootstraps. Lightweight; ~15 lines.

## 8. Rollback plan

Three failure stages, each with an explicit rollback:

### Stage 1 — Sidecar restore fails (most likely, lowest impact)

**Symptom:** pg_restore exits non-zero; sidecar Postgres won't start; or the restored DB is missing tables.

**Rollback:** Stop + remove the sidecar container. Delete the volume. V2 + chat-ai unaffected. Investigate, fix, retry.

### Stage 2 — CSV extraction succeeds, but apply hits a real schema mismatch

**Symptom:** V2 apply starts failing for `historical_*` files (e.g., a new chat-ai column V2 doesn't have, or a constraint violation we didn't anticipate).

**Rollback:**
1. Stop further `historical_*` uploads.
2. Files already on S3 with `historical_` prefix that haven't been processed yet: delete via `aws s3 rm --recursive --include 'historical_*'` (or boto3 equivalent).
3. Files already applied (recorded in `etl_processed_files`): the INSERT ON CONFLICT DO NOTHING means we've only ADDED rows that didn't exist before. **No existing row was modified.** Identify the new rows via `etl_processed_files.rows_applied` — these are the row IDs (filename:row_id) we'd need to DELETE to fully revert. **Tag risk:** identifying exact rows requires the historical CSV files (so we can read row IDs); preserve them in S3 until verification passes.

In practice: if Stage 2 fires, we'd likely accept the partial apply (it's still strictly additive — we got SOME of the missing data) and investigate the schema issue before re-running.

### Stage 3 — Verification fails (drift after all waves apply)

**Symptom:** Layer 1 re-check shows non-zero drift; or Layer 2 sample finds unexplained mismatches.

**Rollback:** No code-level rollback needed — the bootstrap was strictly additive. The drift exists; we investigate WHY and either re-run a corrective pass or document the gap. The sidecar pg stays up for forensics.

### What we will NOT do under any rollback path

- **No** delete-and-rebuild of V2's `messages` or `conversations` tables. The forward incremental data must be preserved.
- **No** restore of V2 from a pre-bootstrap pg_dump. The pre-bootstrap state IS what we've been building since 2026-05-29; rolling back loses 2 days of legitimate forward data.
- **No** touching chat-ai's running services. Bootstrap is read-only against chat-ai's S3 backup; no production chat-ai exposure.

## 9. Execution sequence (proposed)

To be executed **only on Rishi's explicit go-ahead** (this doc, reviewed and approved):

1. **Pre-flight checks** (~15 min)
   - Confirm latest `yral-chat-ai/daily/*.sql.gz` is < 24h old
   - Confirm rishi-5 has > 100 GB free disk
   - Confirm V2 ETL is healthy (`/admin/etl-status` heartbeat fresh, no STUCK marker)
   - **Backup V2 Postgres** per rule #9 (`pre-bootstrap-rebootstrap-<ts>.dump`)

2. **Ship code changes** (~30 min)
   - PR with `scripts/historical_export.py`, `_FILENAME_RE` regex extension, optional migration 024
   - CI + Codex + merge + deploy

3. **Sidecar restore** (~45 min)
   - Provision docker container with mounted volume on rishi-5
   - Download latest backup from S3
   - pg_restore into the sidecar
   - Validate by querying total row counts

4. **Extraction + upload** (~90 min)
   - Run `historical_export.py` against the sidecar
   - 66 message CSVs + ~6 conv CSVs + 1 influencer CSV, uploaded with `historical_` prefix
   - Wave barriers enforced via heartbeat polling

5. **Apply** (~3-5 hours — V2 picks up automatically)
   - Monitor `/admin/etl-status` for `files_processed_24h` growth
   - Watch for `STUCK` markers, integrity verifier failures
   - On any per-file failure: pause uploads, investigate

6. **Verification** (~30 min)
   - Layer 1 count diff: ≤ Option-A skip count
   - Layer 2 random sample: 0 unexplained mismatches
   - Layer 3 boundary message: present in V2

7. **Sidecar teardown** (~5 min)
   - Confirm verification passed
   - Stop + remove sidecar container
   - Delete volume
   - Update `DAILY-LOG.md` with bootstrap outcome
   - Update memory: bootstrap complete date

**Total wall-clock: 6-8 hours, single-operator (me + Rishi watching).**

## 10. Risks + open questions

### Risks (assessed)

| Risk | Likelihood | Mitigation |
|---|---|---|
| Schema mismatch between sidecar and V2 (chat-ai added a column we don't have) | Medium | Apply path already handles unknown columns via header intersection. New columns get ignored; missing columns get DB defaults. Already tested in incremental. |
| Sidecar disk runs out | Low | 50-80 GB volume is plenty for a 5 GB DB + indexes |
| Apply rate is slower than estimated | Medium | 3.3M rows × 99.74% no-op INSERT is still 3.3M COPY-into-staging round-trips. If too slow, ship the SELECT FOR UPDATE lease change. |
| Hetzner egress charges | Low | S3 → V2 (same Hetzner region) is internal traffic, no charges. |
| Bootstrap conflicts with running incremental (race) | Low | Different filename prefixes (`historical_` vs `<ts>_`); `etl_processed_files` UNIQUE on filename rejects any accidental overlap. |

## 11. What "done" looks like

- `etl_processed_files` contains rows for all `historical_*.csv.gz` filenames
- `etl_skipped_rows` for `historical_*` filenames is < 1% of historical rows (conflicts are real cases, not unexpected drops)
- Layer 1 hourly verifier at any pre-2026-05-26 watermark shows `diff == 0 ± skip_count`
- Layer 2 sample of pre-2026-05-26 conversations: 0 unexplained mismatches
- Sidecar Postgres torn down, volume deleted
- `DAILY-LOG.md` entry with row-counts, runtime, any non-fatal anomalies
- `MEMORY.md` updated: "Re-bootstrap complete, A4 satisfied as of <date>"

## 12. What this design does NOT cover

- **chat-ai's own backup integrity:** we trust chat-ai's daily backup is valid. If chat-ai's backup is corrupt, this whole plan fails at sidecar restore — that's a chat-ai team problem to investigate, not a V2 problem.
- **chat-ai schema changes during bootstrap:** if chat-ai ships a migration between when the backup was taken and the bootstrap finishes, the new schema is invisible to us. The bootstrap captures the snapshot at backup time; any later chat-ai changes come through incremental.
- **chat-ai growth beyond 2026-05-26:** out of scope. The forward window is the incremental's job.
- **Performance tuning for the 5-7 hour window:** this design optimizes for correctness, not speed. If we need it faster later, the lease change in 7c is the first optimization.

## Appendix A — Why not just trust the incremental?

If V2 is 99.74% matched and the gap is mostly explainable by Option A skips + the 4-day startup gap, why not just patch the cap logic and call it done?

Because **A4 doesn't tolerate "mostly".** The constraint is "all data must port." 8,566 missing messages, no matter how small a percentage, is a constraint violation. The re-bootstrap is the operation that mathematically proves the constraint is satisfied, not just probabilistically suggests it.
